# How the cards work

The runtime behaviour of the custom elements in `src/cards/`. For every key they take, see [Writing the cards](keys.md); for what they look like, [Design](design.md); for the data three of them read, [Data](data.md).

The cards are Lit elements, as Home Assistant's frontend is. Lit is their one dependency, bundled with them. Each card draws its DOM as an `html` template; what several cards share, and the pieces a large card's file is split into (the pop-ups card's `popup-unfold.ts` and `popup-swipe.ts`), are in `src/cards/parts/`; what reads or draws Home Assistant's own pieces is in `src/ha/`.

A **control** in `chips` or `controls` is one of the following:

| Control     | Is                                                                                                        |
| ----------- | --------------------------------------------------------------------------------------------------------- |
| `toggle`    | A toggling button; `primary: true` fills it                                                               |
| `slider`    | A button that opens a slider over the card                                                                |
| `select`    | An icon that opens a mode menu, or a timer's presets; `primary: true` fills it (the AC's mode button)     |
| `service`   | A button that calls a service                                                                             |
| `nav`       | A coloured icon that opens a pop-up                                                                       |
| `indicator` | A coloured icon, titled with its entity's name and state                                                  |
| `status`    | A named icon, coloured by the first of its `rules` that any of its `entities` matches                     |
| `tyres`     | The tyre icon: orange while a tyre drops, red while one is low                                            |
| `scenes`    | An icon that opens the room's scenes, the active one checked                                              |
| `messages`  | A coloured icon that opens a pop-up, drawn while Home Assistant has messages, their number in its tooltip |
| `dismiss`   | A button that dismisses every Home Assistant notification, drawn while there is one, always asking first  |

- **Visibility and colour.** `show` hides a control by a state rule, and `when` decides its colour. A rule's `is` / `not` lists match the state, or with `attribute` that attribute's value, lower-cased with hyphens removed, and a number as a number (`10000.0` is `10000`).
- **Confirmation.** `confirm`, a state rule matched as `when` is, makes a `toggle`, a `service` control or a toggling glance ask before it acts: while its entity's state matches the rule, the first press arms it, and only a second press within 3 s acts. An empty rule (`confirm: {}`) matches every state, so it always asks, as a `dismiss` control does. A `slider`, a `select` and `scenes` open a slider or a menu first, which is already a second, deliberate step, so they take none.
- **Unavailable devices.** An unavailable entity keeps its place and turns orange: a state prints as an orange "—", a row or chip colours, and a control that acts on it (`toggle`, `slider`, `select`, `service`) is drawn as an inert orange display rather than a button that cannot work. An entity with no value at all (`unknown`) is left out. A list row with `zero_when_empty` is the exception to both: it reads as `0` in its unit, uncoloured. A `status` rule whose `is` names `unavailable` colours an unavailable entity with the rule's colour instead.
- **State lines.** What a `state` line's entries read, and `icon: true`, is in [Writing the cards](keys.md#a-state-line-state).
- **Haptics.** A toggle, a control or a glance, fires Home Assistant's `light` haptic as it acts, a slider `selection` as it commits its value, and a failed call `failure`, as Home Assistant's frontend does: a `haptic` event on `window` (`haptic()` in `src/ha/hass.ts`), which the companion apps turn into a vibration.

[Writing the cards](keys.md) lists every key, and `src/contract/cards.ts` declares them.

## Lifecycle of a card

Every card but the pop-up shell and the template card extends `MnmlCard<C>` (`base.ts`), a `LitElement`. Each card is a shadow root holding its styles and what its `draw(hass, config)` returns. Each card is the `Host` it gives every part it draws: the current `hass`, whether it is on the page (`isConnected`), `hold()`, `register()`, `notify()`, which shows a message as Home Assistant's own toast, and `refresh()`, which draws the card again.

| Step          | What happens                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `setConfig()` | Checks the configuration against the card's structure (`requireCard()` in `keys.ts`): first the keys it does not know, then every required key and every value's kind (`problemsOf()` in `src/contract/required.ts`), then the card's own `validate()`, for what a structure cannot say. Either way HA shows an error card naming each problem by its path ([Rules](#rules)). It drains the holds and teardowns, stores the configuration, collects every entity id in it (any string shaped `domain.object_id`, except a `service`, which has the same shape), and asks for an update |
| `set hass`    | Asks for an update only when one of those state objects, `hass.entities`, `hass.devices`, `hass.locale`, `hass.config` or one of HA's formatters (`localize`, `formatEntityState`, `formatEntityAttributeName`, `formatEntityAttributeValue`) is a new object, as HA's own cards do, so a new language or unit system draws every card again at once rather than entity by entity. While a hold is open no update runs (`shouldUpdate()`), and the last release asks for one                                                                                                           |
| `draw()`      | Returns the card as an `html` template, which Lit lays over the DOM already there, so an element that stays keeps its keyboard focus. It may return `undefined`: the card then hides its own element, so an empty card takes no space and no gap in a pop-up's column                                                                                                                                                                                                                                                                                                                  |
| disconnected  | `disconnectedCallback()` drains the holds and teardowns. A card taken down by a closing pop-up keeps its configuration and its DOM, and comes back live: `connectedCallback()` draws it again on its return, and so does each `hass` after that which changes what it watches                                                                                                                                                                                                                                                                                                          |

State reaches a card through `set hass` only.

### Holds and teardowns

An interaction that a state update must not interrupt **holds** the card (`host.hold()`):

- **A slider**, for the drag, and until 600 ms after its service call has actually landed. A 5 s ceiling keeps a hung call from holding the card for ever. Only the last value sent lets go: a key pressed while an earlier value is on its way waits out its own pause and is sent, and the earlier call's landing neither cancels that pause nor releases the card while a key or a drag is pending. The key pause and the release are two timers (`pause`, `letGo`).
- **An overlay**, or **a menu**, while it is open. Both open through `dismissable()` (`parts/overlay.ts`, an overlay by way of `openOverlay()`), which holds the card, registers the teardown, and closes on a tap outside or on Escape, and a menu on a scroll outside too. It puts focus back on the trigger before it releases the card, so the update that follows leaves focus there.

A press is not a hold. The button card's 600 ms flash is a state of the element (`pressed`), so the state that the press changes draws at once and the flash carries over.

The hold machinery is built so that it cannot get stuck:

- A hold releases once, however often its release is called.
- A drag settles on `lostpointercapture` as well as on `pointerup` and `pointercancel`. So removing the track mid-drag cannot leave a hold open.
- `register(teardown)` records what to undo: the open menu, the open overlay, the weather card's forecast subscription, a large square's history subscription, the messages card's notifications or repairs, a card's place among those counting Home Assistant's messages, a `status` control's wake-up, an armed control's 3 s. `disconnectedCallback()` and `setConfig()` both drain it, zero the holds, and bump a generation counter, so that a release issued before the drain cannot decrement the new count.

The result is that a card torn down by a closing pop-up leaks no listener, cannot drive its hold count negative, and comes back live.

### Stylesheets

A card's styles are `css` values, listed in its static `styles`: the shared ones from `styles.ts` (`BASE_STYLE`, `HEADING_STYLE`, `ROW_STYLE`, `CONTROL_STYLE`, `MOTION_STYLE`), a part's from its module, and the card's own from its file. `ITEM_STYLE` in `parts/item.ts`, for example, is shared by the entity, tile, header and media cards.

- **Adopted, not inlined.** Lit makes one constructible stylesheet of each `css` value, and every element that lists it adopts that one.
- **Why:** a full render has a few hundred cards. Adopting parses about 50 KB of CSS between them, where a `<style>` per card parses more than a megabyte.
- **Fallback:** a browser without constructible stylesheets gets a `<style>` per element.
- **Shared values are custom properties.** A colour several styles share is a custom property on `BASE_STYLE`'s `:host` (`--m-pill`, `--m-hover`, `--m-edge`, `--m-edge-strong`), not a value spliced into each template, so every `css` template is a literal, which the build minifies. The one interpolation is a `css` value inside another: `BASE_STYLE` takes in `MOTION_STYLE`.

## Reading state and calling services

A card reads `hass.states`, `hass.entities`, `hass.devices` and `hass.locale`, and formats through HA's own formatters. A press calls its service through the host's current `hass` (`host.hass`), not the one the button was drawn with: a toggle, a `service` control, the button card, a glance that toggles, a list row's reset, a message's clear, and a menu's choice. A lock or an alarm picks its service from the state at that moment. A slider sends its value through the `hass` its overlay opened with, or the slider card was last drawn with.

- **Readers** (`src/ha/hass.ts`): `stateOf`, `hasValue`, `isOn`, `numericState`, `numberAttribute`, `stringAttribute`, `listAttribute`.
- **Services:** `callService(hass, entityId, 'domain.service', data)`; `callAction(hass, 'domain.service', data)` for one without a target, as dismissing a notification is; and `toggleEntity()`, which calls `lock.lock` / `lock.unlock`, `climate.turn_on` / `climate.turn_off`, or else `homeassistant.toggle`.
- **`ServiceName`** is a closed union, so a typo is a compile error rather than a call that fails at runtime. A new service is added to it.
- **Errors reach the user.** Every call is wrapped in `run(host, promise)`, so a rejection becomes HA's own `hass-notification` toast, with the `failure` haptic, rather than an unhandled rejection in the console.

A large square with a `trend` is the one card that reads history. `subscribeDay()` (`src/ha/history.ts`) subscribes to `history/stream` for that one sensor over the last 24 hours (`minimal_response`, `no_attributes`, `significant_changes_only: false`) while the card is on the page, and keeps the points the day covers and the one it starts in; the subscription is one of the card's teardowns. A message whose `start_time` reaches back to the asked start replaces the day: the first one, and the one a reconnect sends. Every other message joins it in time order: the live ones, and Home Assistant's catch-up, which starts a microsecond after the last point of the first. The line takes 97 samples of the day, one each 15 minutes, each the last value at or before it; a value that is not a number, or a time before the first point, is a gap in the line. It spans the day's lowest to highest value, or 2 around their middle when they are closer, so a steady reading draws a flat line across the middle. Until the first message, or with no number in the day, the square draws no line.

## Names, formatting and icons

**Names** (`src/ha/names.ts`):

- `entityName()` is `hass.entities[id].name`. Failing that, it is the friendly name without the device name HA prefixes for `has_entity_name` entities. An empty name, HA's "Use device name", counts as none, so the entity prints its device's name.
- `nameOf()` applies a card's naming options:
  - `label: 'device'` names a row, an item or a header after its device (`name_by_user`, then `name`);
  - `strip` removes a literal suffix;
  - `strip_word` removes a word, with its optional plural and leading space, wherever it falls; when it was the first word, the new first letter is capitalised, so "Tailscale router" reads "Router".
- `deviceSerial()` reads the device's `serial_number`.

**Formatting** is HA's own:

- `hass.formatEntityState()` gives precision, unit and translation.
- `hass.formatEntityAttributeValue()` has a fallback that capitalises a raw word HA does not translate, such as a swing mode.
- A timestamp, and when a state last changed (`since`), is `ha-relative-time`.
- A timer's time left (`remaining`, `src/ha/timer.ts`) reads `m:ss`, or `h:mm:ss` from an hour, rounded up. While the timer is active it counts down from `finishes_at`, redrawn at each second by `countdown()`, a directive that stops ticking once the line leaves the page or the time is up; while it is paused it is the `remaining` attribute, and while it is idle Home Assistant's word for the state.

**A card's own words** are the ones Home Assistant does not translate, and they come from a word table, one per language, in `src/words/`:

- **Which table.** `wordsFor(hass.locale.language)` picks the table of the profile's language (`ro`), then of its base language (`ro-MD` reads `ro`), then English. A language with no table draws English words beside Home Assistant's own states, attribute names and values, in its language.
- **What is in it.** The back and close buttons; the labels of the buttons that have no entity (`Show ...`, `Hide ...`, `Clear ...`, `Reset ...`, `...: choose`, `Show the lights of ...`, and the media card's `Previous`, `Play`, `Pause`, `Next` and `Volume`); an armed control's question (`Unlock? Tap again`) with the actions a toggle names from its entity's state; the tyres chip's titles; a square's count of the chips its strip leaves out (`2 more`); the car plan's parts, each with its own `open` and `half open` (so a language can agree them with the part), and its summaries; the list card's `Lowest ...` and `Highest ...`; the clients card's headings, connections and count; what a conflict adds to a glance's line; the report card's heading and count; the weather card's heading and `Today`; the agenda's weeks, notes and episode count; the messages card's empty states. Apart from them, under `templates`, are the words the templates show, the headings, table headers, chip, control and glance names, state texts and rule words of every shipped template, which a template names as `'[[words.lights]]'` ([Templates](templates.md#writing-a-template)).
- **What is not.** Every state, attribute name and attribute value is Home Assistant's, through its formatters, the weather card's facts included (`formatEntityAttributeName`). A date, a weekday, a time and a number are `Intl`'s in the profile's language, and so are the minutes of a seconds counter (`minutes: true`, `5 min` in English, `5 min.` in Romanian). The `—` for a missing value (`DASH` in `src/ha/format.ts`) and the `•` between parts are glyphs, not words. A title, a header, a `words` dictionary and a `text` entry are the author's, in the configuration; a template writes its own as words of the tables, so a template card shows them in the profile's language. A note meant for the author (a card that is set up wrong, a template that fails) and a repair's title from its id when Home Assistant has no words for it stay in English.
- **The shape.** English (`src/words/en.ts`) is the source, and its type (`Words`) is every other table's, so a table that misses a word, or adds one, does not type-check. A word that takes a value is a function (`show: (name) => ...`), so each language puts the value where its grammar wants it; a count is a function too, with the language's plural rules (`Intl.PluralRules`). A template's word is plain text, since a template passes it no value, and is named in lower case and `_` (`all_lights`), as a template writes a slot.
- **Adding a language.** A new file `src/words/<language>.ts` exports a table typed `Words`, and `TABLES` in `src/words/words.ts` maps the language's code to it. The words follow Home Assistant's own translation for that language where it has the same word, and use the language's proper letters (`ș` and `ț` in Romanian, not the cedilla).
- **Held by tests.** `src/words/words.test.ts` checks the choice of table, the counts and the punctuation. `src/cards/languages.test.ts` draws the cards in Romanian and in German, and then in a pseudo-language whose table and Home Assistant words are all marked: a Latin letter left outside the marks is an English word that bypassed the table, and fails the test. `src/templates/words.test.ts` checks that every word a shipped template names is in the tables, that every template word is named by one, and that no shipped template shows a literal in English; `src/cards/template.test.ts` draws a template in Romanian, in a language with no table, and across a change of language.

**The state line** (`stateLine()` in `src/ha/format.ts`) is one `span` per shown item, separated by `•`:

- Each span is an inline flex box that centres the icon on the text, 3 px from it. Its text sits in a `.value` box of its own, so a part wider than its line, as in a tile at half a narrow section, ends in an ellipsis rather than a clipped glyph.
- `vertical-align: top` keeps its baseline the line's.
- The icon's `line-height` is 0, so that `ha-icon`'s inline strut doesn't push it below the text.
- Every item follows its `when` rule, a `text` included, so a line can read "None" while a count is 0 and the count otherwise.

**Icons** are HA's elements:

- `ha-state-icon` for an entity.
- `ha-attribute-icon` for a preset or swing mode.
- `ha-icon` for a literal.
- The HVAC modes are the exception: they use `HVAC_ICONS` (`parts/menu.ts`, HA's own icons for them). `ha-attribute-icon` has none, and an entity's custom icon would override the state icons.

## Rules

**Unknown keys are errors.** A key a card does not know, at any depth it checks, makes it an error card that names the key and its path (`unknown key: rows[1].lowes`). The layout keys Home Assistant and card-mod add (`grid_options`, `visibility`, `view_layout`, `layout_options`, `card_mod`) are allowed at the top. The cards a pop-up holds are checked by those cards; the shell checks only their `visibility`.

**So are missing and wrong values.** `problemsOf()` (`src/contract/required.ts`) reads the card's structure in `src/contract/structure.ts`, the same one its known keys and its editor come from, and checks every key it describes, at every depth: a part, each entry of a list, and the kind that a tagged entry's `type` or a marked card's marker picks (a `slider` control needs its `name` and `icon`, a tile with a `name` its `icon`). A required key must be there and not empty, and a value must be of its key's kind:

| Kind                                | Must be                                                                                                           |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| A text, an icon                     | a string                                                                                                          |
| Texts, a rule's `is` and `not`      | a list of strings, so `'on'`, `'off'` and numbers in a rule are quoted; an alert's `screens` a list of its values |
| A number, a share                   | a number                                                                                                          |
| A flag                              | `true`, or `device` for `label`                                                                                   |
| A choice, a colour                  | one of its values; a colour one of `red`, `orange`, `amber`, `blue`                                               |
| An entity, entities, corners        | `domain.object_id` of the key's domains (a messages card's `entity` is a `sensor`); corners four of them          |
| A pop-up, a service                 | a hash (`'#kitchen'`); `domain.service`                                                                           |
| Words, a summary                    | a mapping of states to words (to a colour for `colors`); `lowest`, `highest` or `{ sum: n }`                      |
| A rule, a part, parts, cards, slots | a mapping checked by its own structure; a list of them; a list of cards with a `type`; a mapping                  |

The error names every problem at once, by its path: `rows[0].entity is required; controls[1].popup must be a pop-up hash, such as '#kitchen'`. The pop-up shell and the template card make the same check. A card's own `validate()` keeps only what a structure cannot say: the clients card's subnets, a glance's `confirm` without `toggle`, a `total` with a key that colours or counts, and a list with both `lowest_first` and `highest_first`.

**Sizes.** In a sections view, the button, select, slider and tile cards ask for half a section (6 of its 12 columns), the pop-up shell for 1, and every other card for the full section, each with its own height (`getGridOptions()`). `grid_options` overrides it.

A **`StateRule`** (`attribute`, `is`, `not`) matches the normalised state, or with `attribute` the normalised value of that attribute (`holds()` in `src/ha/rules.ts`). An attribute the entity lacks, or one that is a list or a mapping, reads as `unknown`, so a `not` rule shows it and it never colours; an unavailable or missing entity reads its state as before.

- **Normalising** (`normalise()`) reads a number as a number, so `0.0` is `0`; it lower-cases any other state and removes its hyphens, and reads a missing entity as `unavailable`. The rule's own entries are normalised the same way. So a rule may use the integration's spelling (`SELECTIVE-LOCKED`) or the normalised one (`selectivelocked`), and the same holds for `words` keys.
- **`EntityRule`** reads another `entity`: the current room while the vacuum is `cleaning`, or the mop drying time while the mop drying switch is `on`.
- **`when`** decides a colour, and **`show`** a visibility. A coloured pill, control or header without `when` lights on `on` (`active()` in `src/ha/rules.ts`); a list row without `when` is coloured whenever it is shown, since a flag carries its condition in `show`.
- **A `status` control's `rules`** are tried in order. The first one that any of its `entities` matches colours the chip. The tooltip lists those entities with their states, named and worded as a list row's are: a rule's `label: 'device'` names them after their device, and its `words` renders their raw states.
- **A `within_days` rule** holds while its timestamp is that many days off or less, judged against the clock at each draw. A page left open wakes its card for it (`refresh()`, through a teardown it registers): when the soonest of those timestamps comes within its days, or after an hour, whichever is first. So a key that comes due turns red on time, with no state change to draw it. Only a card on the page sets a wake-up, so a card a closed pop-up dropped keeps no timer; one that comes back draws again and sets it anew.

**No value means no row; unavailable means orange.** `hasValue()` and `isUnavailable()` in `src/ha/hass.ts` split a missing value in two:

- **No value** (`unknown`, `none`, empty): the row or state item is not shown, so nothing hides a missing value by hand. A scene, a button or a sensor the device has not reported yet has nothing to say.
- **`unavailable`**: the device is offline, which is a warning, so the element keeps its place and everything of it that takes a colour is `UNAVAILABLE` (`src/ha/rules.ts`), the orange of [Design](design.md#colour). Where its value would print, an em dash `—` stands (`unavailableValue()` in `src/ha/format.ts`): a `role="img"` glyph whose `aria-label` is HA's own word for the state, so a screen reader hears "Unavailable" rather than "em dash". The dash is the same glyph a table cell and the car plan print for a value that is missing; the colour is what tells the two apart.

## Controls, sliders and menus

- **Controls** (`parts/controls.ts`): `renderControls()` draws a lane. `colorStyle()` (`src/ha/templates.ts`) sets `--m-color` to `var(--<color>-color)`, which the `colored` class reads; `tint()` picks the colour from the rule, or orange for an unavailable entity. A toggle also says `aria-pressed` from its entity's state, not from the rule, as Home Assistant's own toggles do: pressed while the entity has a value that is not `off`, nor `locked` for a lock, `disarmed` for an alarm or `closed` for a cover (`isOn()`). So a toggle coloured while `off`, as AdGuard's protection is, is not pressed then.
- **Sliders** (`parts/slider.ts`, with each `SliderKind`'s range, format and service call in `sliderSpec()`, `parts/slider-spec.ts`): a slider button opens its slider, an `mnml-slider` element, as an overlay over the card; the slider card draws the same element in place. The overlay closes on its X, the round close button after the slider, which gives the focus back to the slider button, 3 s after the last touch, or on a tap outside.
  - Opened from the keyboard (a click whose `detail` is 0), the slider takes the focus once it has drawn, and the overlay stays open while the focus is in it. Opened by a pointer, the focus stays where it was, so the 3 s close runs.
  - On a heading, the overlay covers the heading (`.heading` is positioned in `OVERLAY_STYLE`), with no inset, and its slider is as tall as the heading's controls, 36 px.
  - A drag sets the value when it ends.
  - The keyboard uses the arrow keys, Home and End, and commits 500 ms after the last key, or at once when the slider closes before then. A value sent as the slider closes goes through `run()` like any other, so its failure is a toast.
- **Menus** (`parts/menu.ts`) are popovers built with the browser's popover API. `sceneChoice()` turns a `scenes` list into options named and iconed by the scene entities, each calling `scene.turn_on`. Its current option is the scene whose name is the state of the `active_scene` select. `presetChoice()` turns a timer's presets into options that call `timer.start` with that `duration`: `timerPresets()` (`src/ha/timer.ts`) reads them from the timer's registry entry (`config/entity_registry/get`, its `options.timer.presets`, in seconds), whole, above zero and each once as Home Assistant keeps them, asks once per timer until `hass.entities` changes, and draws the card again when they come.
  - A menu is a `role="menu"` of `menuitemradio` items with `aria-checked`, or of plain `menuitem`s when there is no current value, as for scenes with none active. Its trigger carries `aria-haspopup="menu"` and `aria-expanded`.
  - Its trigger toggles it. A tap on the trigger, or anywhere on the select card's row, while its menu is open closes the menu: `dismissable()` counts the trigger as inside (`trigger`), and `openMenu()` closes the menu its anchor already has rather than opening a second one.
  - It opens with the current item focused and scrolled to the middle of the menu, so a long list such as 19 scenes shows it. The arrow keys move with wrap-around, Home and End jump, Tab and Escape close it, and a choice, Escape or Tab put focus back on the trigger.
- **Folds** (`section()` with a `Fold`, `parts/section.ts`): the heading of a folding list or clients network is the tap target, and its chevron is a `button` with `aria-expanded`, labelled with the title. A tap toggles the card in place, and the card keeps the choice (`choice`, `choices`) until the page reloads; until then, `open` comes from the card's own rule. Unfolding scrolls the section into view (`scrollIntoView` with `block: 'nearest'`, smooth unless reduced motion is set), in the pop-up's own scroll area or the page, whichever holds it; a section taller than the room shows its heading at the top. Folding never scrolls.
- **Confirmation** (`parts/confirm.ts`): a press on a control whose `confirm` holds arms it rather than acting, and draws the card again (`refresh()`). Armed, the control shows the question in place, `Unlock? Tap again` in the primary text colour, and is labelled with it and its entity's name (`Unlock Front door? Tap again`); a `service` control asks by its `name` (`Clear all? Tap again`), a toggle by the action its press takes now (`toggleAction()` in `src/ha/hass.ts`, beside `toggleEntity()`, so the two agree). A second press within 3 s acts, through the host's current `hass`; otherwise the control lets go and draws again. The rule is judged at the press: a state that no longer matches acts at once. The 3 s is a teardown, so a card reconfigured or taken off the page keeps no armed control.
- **Tooltips on touch** (`parts/tooltip.ts`): a touch held 500 ms on an element with a tooltip (a control, a chip, a glance, an icon button) opens its tooltip and does not act: the click that follows is swallowed before the element or the card around it sees it, and the browser's own long-press menu is cancelled. A shorter touch acts as before; moving off the element, or a scroll (`pointercancel`), lets go. Lifting the finger leaves the tooltip open, and the next touch anywhere closes it. Hover and keyboard focus open it as [Design](design.md#tooltips) says.
- **Overlays** (`openOverlay()`, `parts/overlay.ts`): a slider's, and a large square's menu and its lists, each over its card. One holds the card through `dismissable()`, except a square's menu, which is `live` and leaves the card drawing so that it follows the state; it keeps its clicks from the card under it, and closes on its close button (`closeButton()`) when it has one, Escape, a tap outside, or 3 s after it opens, after the focus leaves it, after its slider last moved or after its list last scrolled, while the focus is not in it. A close by its button, Escape or a choice gives the focus back to what had it when it opened. `redraw()` draws it again in place, for an overlay that follows the state.
- **A large square's menus** (`parts/square-menu.ts`): `lightsButton()` opens the light's menu, and `navButton()` the menu of a `nav` chip with `controls` in the column. A menu is a toggle of the button's entity (`aria-pressed`) at the column's foot, then the options `squareOptions()` makes of the controls, each while it is shown and has something to offer: a `scenes` list, a `brightness`, `color_temp` or `temperature` slider, and a `select` other than a timer's, named and iconed by its current option. A `nav` chip's menu has the toggle only when its controls hold a `toggle` of its entity (`powered()`), so an AC, which turns off by its mode, has none, and it ends with Details, which opens its `popup`. The button has `aria-haspopup` and `aria-expanded`, true while anything it opened is open. An item with nothing to offer has no menu: its button is the toggle itself. A `nav` chip with nothing to offer is drawn as a chip, and opens its pop-up.
  - A tap or click opens the menu in the column's place, and neither toggles the entity nor opens the pop-up. Its buttons grow out of the button tapped into their places (`expandFrom()`, [Motion](#motion)).
  - The toggle toggles the entity and leaves the menu open, restarting its idle close. Each draw of the card draws the open menu again with its `hass`, so the toggle shows the entity's state and the options come and go with their show rules, a light turned on gaining its sliders and an AC turned off losing its temperature.
  - Opened from the keyboard (a click whose `detail` is 0), the toggle takes the focus. An option picked by the keyboard opens its list or slider with the focus in it.
  - A list is a `role="menu"` of the menu rows (`menuRows()`), labelled with its entity's name, scrolled to the current option, and moves with its keys (`menuKeys()`): the arrow keys with wrap-around, Home and End, and Tab and Escape close it.
- **Escape closes one layer.** A menu or an overlay consumes its Escape (`preventDefault()`), so the dialog's close watcher doesn't close the pop-up underneath in the same keystroke.

## Navigation

Navigation is HA's own mechanism (`src/ha/navigation.ts`), and **the URL is the only state a pop-up has.**

- `navigate(hash)` pushes the hash with a `depth` in its state, one more than the pop-up it was opened from, and dispatches `location-changed`.
- `closePopup()` goes back `depth` entries, to the view's own entry, so a closed pop-up leaves nothing in history and the browser's back button leaves the dashboard. A pop-up that `navigate()` did not open, from a link or a reload, has no depth: it replaces its entry with the URL minus its hash, keeping HA's root marker.
- `back()` goes back one entry from a pop-up opened from another one, and closes it otherwise.

**Links.** `linkTo()` (`parts/item.ts`) makes a row and its pill a way into a pop-up: an item with a `popup`, and the media card with one.

- Both build the pop-up ahead on `pointerdown` (`prebuild()`) and open it on click, and both stop the event, so a link inside a tile doesn't also open the tile's pop-up.
- The pill is the keyboard path (`onPress()`, Enter or Space), labelled with the row's name.
- The row's own controls stop their taps, so the media card's transport, volume and power buttons work without opening anything.

## The pop-up shell

Every pop-up of the dashboard lives in one `mnml-popups-card` (`cards/popups.ts`).

**Why one shell.**

- It draws no state of its own, so it is not a `MnmlCard`: it watches no entity, and draws again only when the hash opens, changes or closes a pop-up, while its children get each `hass` from it directly. A `MnmlCard` would watch every entity its pop-ups name.
- One shell costs four window listeners (the three route events and the prebuild request) and one route callback per hash change, however many pop-ups there are; with `idle_close`, six more while a pop-up is open. That keeps a second view affordable: duplicating one card doesn't multiply anything.
- It asks for one grid column, the smallest span, and its host has no height, so it takes one zero-height grid row. `width` is the dialog's width on a wide screen, and the width of every pop-up that unfolds.

**A real `<dialog>`.** It opens with `showModal()`, which gives the top layer (no ancestor can clip it), `::backdrop`, Escape, the focus trap and modal semantics for free. Its `aria-label` is its header's name: the first card's `name`, or failing that its `entity`'s name (after its device with `label: 'device'`). `cancel` and a click on the backdrop turn into `closePopup()` rather than being handled directly, so the hash stays the single source of truth. The shell never opens or closes itself: it follows the hash.

**Routing waits for the page.** HA configures a card before it inserts it, so `setConfig()` routes only while the element `isConnected`. Otherwise, a dashboard loaded at a URL that already carries a pop-up hash would call `showModal()` on a dialog in no document, which throws. The attempt would already have claimed the hash, so `connectedCallback()` would see nothing to do and the pop-up would never open. Configured while detached, the card waits, and `connectedCallback()` opens it.

**How a pop-up opens.** The shell picks `open`'s choice for the screen: `phone` up to 600 px, `tablet` up to 1024 px, then `desktop`; left out, a sheet on a phone and a dialog elsewhere. The choice is a class on the dialog (`sheet`, `dialog`, `unfold`), so the styles follow the setting rather than a media query.

**The scrollbar sits between the cards and the panel's edge.** The body, which scrolls, ends 5 px short of the panel's end edge, where the scrollbar is, through the panel's padding (`mnml-popup-gap`), and keeps 6 px clear on its content. A thin scrollbar then has about the same air on both sides, and an overlay scrollbar on a phone draws in that strip, never over a card. Home Assistant's own `scrollbar-color` styles the thumb, so the card sets only its width and place.

**A shadow while there is more.** The panel's bottom edge darkens (`mnml-popup-scroll-shadow`) while its body has more below it, and clears when the body is scrolled to the end. A scroll, and a resize of the body or of any card in it (a list unfolding, a card loading), re-measure it.

**Unfold.** A pop-up set to `unfold` opens out of what it was opened from, its origin: a tile, a row, a chip or a glance (`parts/popup-unfold.ts` holds the panel's place and clips, the scroll that makes room, the wait for an origin to settle and the following of the origin):

- **Where from.** A tap records what it came from: `navigate(hash, from)` keeps the origin. A tapped glance or `nav` chip is its own origin, the badge itself and not the strip or the tile around it; a tapped row names the card whose shadow root holds it (`openedFrom(event)`); and every tile offers itself for its own `popup` each time it draws (`offerOrigin`). An origin that has left the page is no origin, and a pop-up without one opens as a dialog.
- **Its place.** The panel is the shell's `width` wide, never wider, whatever the width of its origin, and no wider than the window less 8 px at each side. It starts from the origin's edge nearer the window's: an origin in the left half grows right from its left edge, one in the right half grows left from its right edge; either way it stays 8 px inside the window. It grows down from the origin's top, or, with less than 420 px below the origin and more room above, up from the origin's bottom. It scrolls inside when it is taller than the room it has.
- **Scrolled into view.** Before it opens, the page scrolls (smoothly, or at once with reduced motion) so that the origin has 420 px below it, or, when the origin is cut off at the top, so that its top is in view. The scroll goes no further than the page allows, and an origin that already has the room does not move the page. Where the page cannot scroll enough, the panel opens upward or scrolls inside, as above.
- **Its look.** The panel is revealed from the origin's rectangle outward with a clip, in 300 ms, so its text never squashes, and folds back into the origin when it closes. The backdrop is lighter than a dialog's, and the panel is a card: the cards' fill, edge, highlight and the pop-up's shadow. With reduced motion it opens in place without the animation.
- **It stays with its origin.** While it is open, the panel follows its origin on events (`following()`): a scroll of the page or of a scroller around the origin (a capturing listener on the window and on each shadow root the origin sits in), a resize of the window, and a change of size of the origin or of anything it sits in (one `ResizeObserver`) each wake a frame loop that re-measures the origin and moves the panel with it, and that stops once the origin has kept still for 6 frames. So a resize or a late layout carries it along, and a pop-up left open on a still page runs no frame at all; closing it lets go of every listener. A pop-up opened from inside it takes over its place and its origin, so Lights inside a room swaps the content without moving.
- **On a page load.** A dashboard loaded at a pop-up's hash has no tap: for that hash, the shell waits up to 600 ms for its tile to offer itself, and until the tile has kept still for 6 frames (at most 1.5 s), since the cards above it are still drawing and moving it. A nested pop-up's row is not on the dashboard after a reload, so it opens as a dialog. A pop-up whose hash clears while it waits does not open: each open and each close takes a turn (`turn`), and an open goes on only while its turn is the last.

**Pop-ups from other cards.** A template card gives the shell its pop-ups through `parts/popup-registry.ts`: `announce(owner, popups)` while it is connected, `withdraw(owner)` when it leaves. The shell looks a hash up among its own `popups` first, then the announced ones in the order they came, the first owner of a hash keeping it. A hash announced twice, or announced and also in the shell's own `popups`, is a console error, reported once until the announcements change. An announcement re-routes, so a pop-up whose hash is already in the URL opens as soon as its template card announces it.

**Children are built lazily.** A pop-up's cards are arbitrary Lovelace cards, built by `cardOf()`: an MNML card by its own class, any other through HA's `loadCardHelpers().createCardElement()`. So its children are typed only as Lovelace cards (`LovelaceCardConfig`), and the two keys of theirs it reads, `visibility` and `entity`, as unknown values that `src/ha/conditions.ts` reads.

- They are built on open and dropped on close. A tile asks for a build ahead on `pointerdown` (`prebuild()`), so the dialog opens already filled. A link inside the tile (a pill, a row, a `nav` chip) stops that `pointerdown`, so only its own pop-up is built ahead.
- A build in flight is shared: a second request for the same hash, or the open itself, waits for it rather than building again.
- They receive `hass` on every state change.
- **`visibility` is the shell's.** A child is the bare card, not the `hui-card` wrapper that evaluates `visibility` in a view. So the shell judges a child's conditions itself, as Home Assistant's frontend does (`Judge` in `src/ha/conditions.ts`), on build, on every `hass` and on every answer, and sets `hidden` on the card; a hidden child takes no space.
  - **In the browser:** `state` and `numeric_state`, with `attribute`, a state or a bound that names an entity reading that entity's state, and the card's own `entity` standing in for one the condition leaves out; `screen`, through `matchMedia`, whose changes judge again; `user`, by Home Assistant's user id; and `and`, `or` and `not`, which skip a condition with `enabled: false` and hold without conditions. A condition whose `enabled` is a template is unknown, so it hides.
  - **On the server:** every other kind (`sun`, `template`, `zone`, `device`, an integration's own, and a `state` or `numeric_state` written with core's `entity_id`) is sent to Home Assistant with `subscribe_condition`, one subscription for each, held while the pop-up is open and sent again on a new connection. The card is hidden until the answer comes, and while the answer is an error.
  - **Shown:** `time`, `location` and `view_columns`, which Home Assistant judges only in its own views, never hide a card.
  - A condition that is not a mapping, or a `state`, `screen` or `user` condition that lacks the key it is judged by, is an error at `setConfig()` that names its path. Every condition Home Assistant's editor writes, its empty new ones included, is accepted.
- **Idle close.** With `idle_close`, an open pop-up closes after that many seconds without input: a pointer, a key, a wheel, a touch or a scroll anywhere in the window (capturing, passive listeners, held only while a pop-up is open), or a state change whose context is the reader's own user. It closes as the close button does (`closePopup()`), so the URL stays the only state.
- **Alerts.** Each of `alerts` watches its `entity`, matched as `when` is (`on` by default, and never while the entity has no value). A change into a matching state opens its pop-up with `navigate()`, unless `screens` or `users` leave this screen or reader out, or the pop-up is already open; the first `hass` only records where each alert stands, so a dashboard loaded while one holds opens nothing. When the state clears, the alert closes the pop-up with `back()`, if it opened it and its hash is still the URL's. An alert whose hash no pop-up has, its own or an announced one, opens nothing and says so once in a toast.

**Scrolling stays inside.**

- While a pop-up is open, the page behind it doesn't scroll.
- A drag inside content that can scroll, or inside a nested scroller of its own, is left alone.
- A drag on the header, on the backdrop, or inside content that cannot scroll is cancelled rather than passed to the page.
- **A swipe down closes it,** however it opened: a sheet, a dialog or an unfolded panel (`parts/popup-swipe.ts`, whose handlers the shell puts on every panel). A touch or pen drag that starts in the top 88 px of the panel, with the content not scrolled, pulls the whole panel down with the finger once it has moved 10 px; a mouse never does, and a drag that goes up first, or starts lower, is left alone. Past 80 px, or as a quick flick of more than 20 px, the panel slides off the screen in 200 ms and the address is cleared at once, as the close button does (`closePopup()`, so a pop-up opened from another closes with it); a shorter, slower drag springs back in 180 ms. With reduced motion the pop-up goes at once.

## Motion

Motion is short, and only where something appears or leaves (`src/ha/motion.ts`, `MOTION_STYLE`):

| What            | Enters                                                        | Leaves                                                                                         |
| --------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Backdrop        | fades in (`mnml-fade`, 140 ms)                                | fades out with the dialog (`dialog.leaving::backdrop`)                                         |
| Dialog          | rises (`mnml-rise`, 160 ms)                                   | a 6 px fade over `FADE_LEAVE`                                                                  |
| Sheet           | slides up from the bottom (`mnml-sheet`, 220 ms)              | slides back to `translateY(100%)` over `SHEET_LEAVE`                                           |
| Unfolded pop-up | unclips from its origin (`UNFOLD`, 300 ms)                    | folds back into its origin over `FOLD`, or fades as a dialog when the origin has left the page |
| Scenes menu     | rises (140 ms)                                                | none                                                                                           |
| A square's menu | each button grows out of the button tapped (`EXPAND`, 180 ms) | none                                                                                           |

- **Leaving is animated.** A CSS animation cannot do this for an element about to be removed. So `shut()` runs the leaving keyframes through the Web Animations API (`leave()`) and closes the dialog when they finish.
- **The dialog draws no focus ring.** `showModal()` focuses the dialog itself, which fills the viewport, so its ring would frame the whole page; a Tab moves on to its first control, which draws its own.
- **One pop-up to another keeps the dialog, and the panel.** Routing from an open pop-up to another changes only what is in the panel: the old header and body slide 20 px aside and fade (110 ms), the new ones slide in from the other side (200 ms), and the panel's height morphs from the old to the new. Opening goes in from the end of the line (the right, in a left-to-right language) and going back, by the back button or the browser's, from its start, by the history's depth. So the backdrop stays as it is rather than fading out under a new one fading in, and an unfolded pop-up keeps its place. With reduced motion the content is replaced at once.
- **One choice of opening.** `SHEET` (600 px) and the tablet's 1024 px are read only by `narrow()`, to pick `open`'s choice; the layout and the animation follow the class that choice puts on the dialog, so they cannot disagree.
- **Reduced motion.** `reduced()` skips all of it and closes at once. `MOTION_STYLE` turns every animation and transition off under `prefers-reduced-motion: reduce`.
- **Only there.** Only what the cards build and remove animates: pop-ups, menus, overlays and press feedback. **A value never animates:** no transition sits on a value, a fill or a state's colour, so a slider's fill follows the finger exactly during a drag, and arrives instantly from the state.

## The YAML writer

`src/contract/yaml.ts`, the writer of `build()`'s dashboard and the demo's package, writes YAML 1.1, the version HA's loader reads, without merge keys. It single-quotes, wherever they appear, both as values and as mapping keys, every string that loader would read as something else:

- the YAML 1.1 booleans (`on`, `off`, `yes`, `no`, `y`, `n`);
- numbers in YAML 1.1's forms: sexagesimals (`3:1`), with underscores (`1_000`), binary (`0b101`);
- dates (`2026-10-13`);
- `=` and `<<`, which that loader refuses unquoted;
- and what a YAML 1.2 reader, the MNML panel's, reads as a number (`0o17`, `1e3`).

That keeps them strings: a `words` key of `on` would otherwise load as `true` and never match. The writer also quotes whatever else needs it, a hex colour for one. A configuration written by hand, or by another generator, needs the same care: quote `'on'` and `'off'` where they are strings. A string that needs no quotes stays plain.

## What Home Assistant's frontend provides

What the cards take from HA's frontend, which only the live instance can confirm; the first suspects when something reported from it looks wrong.

- **Formatting.** `hass.formatEntityState()` and `hass.formatEntityAttributeValue()` give precision, units, translations and the brightness in percent. So a sensor with no display precision shows every decimal it reports; set one in the entity's settings. The car plan formats the tyre pressures itself, and reads the same setting (`display_precision` in `hass.entities`). A utility meter with no value shows "—".
- **The registries.** `hass.entities` and `hass.devices` provide the names, and the `serial_number` a `serial` entry prints. An entry whose device has none prints nothing.
- **Locale.** `hass.locale` becomes a new object when the profile's language changes.
- **Icons and time.** `ha-state-icon` follows the state. `ha-attribute-icon` knows the preset and swing modes it knows; a swing mode it has no icon for shows none. `ha-relative-time` renders timestamps.
- **Pop-up plumbing.**
  - `loadCardHelpers().createCardElement()` returns the bare card, not a `hui-card`, as `cardOf()` does for MNML's own. So the shell passes `hass` to a card inside a pop-up and evaluates its `visibility` itself, and so does the template card for the card it draws.
  - `subscribe_condition` judges the conditions the browser cannot, and answers `{ result }` or `{ error }`.
- **Haptics.** Home Assistant's frontend and the companion apps listen for the `haptic` event on `window`.
- **Notifications and repairs.** `persistent_notification/subscribe` sends the notifications (`current`, then `added`, `updated` and `removed`), and `persistent_notification.dismiss` takes a `notification_id`, while `persistent_notification.dismiss_all` takes nothing. `repairs/list_issues` answers an administrator only, and `repairs_issue_registry_updated` fires when the issues change; a repair's words are Home Assistant's `issues` translations, loaded with `hass.loadBackendTranslation()`. The cards that count them, a `messages` control, a messages glance, a header with `messages` and the messages card's count, share one subscription to each (`messageCount()` in `src/ha/message-count.ts`): the first card on the page to ask starts it, a new connection or a change of administrator starts it again, and the last card to leave the page ends it. The count is not known until every subscription has answered, and a card draws no count until then.
- **Timers.** A timer's `finishes_at` and `remaining` attributes, and its presets in its registry entry's options.
  - `location-changed` reaches the pop-up shell.
  - `history.state` holds HA's root marker.
  - `show_header: false` leaves a drag strip and no header.
  - The map card's height comes from `aspect_ratio` inside a pop-up.
- **Template families.** The template card fetches the shipped families, `mnml-cards-<family>.json`, from beside the bundle: their URLs resolve against the bundle's own (`import.meta.url`), so they come from wherever the bundle is served (the integration's `/mnml-files/`), and a family's `?v=` comes from the bundle.
- **Templates.** The template card subscribes to the integration's store with `mnml/templates/subscribe` ([Where templates live](templates.md#where-templates-live)). The template card, the pop-up shell and the MNML panel draw MNML's cards themselves; a Home Assistant card in a template or a pop-up is drawn with `loadCardHelpers()` when the page has it, as every dashboard does, and is otherwise a note saying it shows once a dashboard has been opened in the tab. The panel loads Lovelace's module, which brings `loadCardHelpers()`, through `partial-panel-resolver`'s `_getRoutes()`, which is not a promised API, only so that `ha-form` can load; when the form does not come, the panel's head and each editor say so, and what to do. Discovery reads `hass.areas`, `hass.devices` and `hass.entities`, the last with `platform`, `translation_key` and `entity_category`.
- **Browser APIs.** The popover API, for the menus. And `lostpointercapture` firing at a capture target that was removed from the document: that is what settles a drag when the slider overlay closes under a held pointer, and it is the one thing between that and a hold that never releases.
- **Dark mode.** A theme's `modes`, the MNML theme's included, follow the operating system through each profile's dark mode setting (Auto), not through the theme.
